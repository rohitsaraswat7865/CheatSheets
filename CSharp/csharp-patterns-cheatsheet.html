📐 SOLID Principles

SOLID is an acronym for five design principles that make software designs more understandable, flexible, and maintainable.

SSingle Responsibility Principle (SRP)

Definition: A class should have only one reason to change, meaning it should have only one job or responsibility.

Why It Matters:

  • Easier to understand and maintain
  • Reduced coupling between components
  • Easier to test in isolation
  • Changes in one area don't affect others
❌ Violating SRP 
public class Employee
{
    public string Name { get; set; }
    public decimal Salary { get; set; }
    
    // Responsibility 1: Employee data
    public void UpdateEmployee() { }
    
    // Responsibility 2: Salary calculation
    public decimal CalculateSalary() { }
    
    // Responsibility 3: Reporting
    public void GenerateReport() { }
    
    // Responsibility 4: Database operations
    public void SaveToDatabase() { }
}
✅ Following SRP 
// Only handles employee data
public class Employee
{
    public string Name { get; set; }
    public decimal Salary { get; set; }
}

// Handles salary calculations
public class SalaryCalculator
{
    public decimal Calculate(Employee emp) { }
}

// Handles report generation
public class EmployeeReportGenerator
{
    public void Generate(Employee emp) { }
}

// Handles persistence
public class EmployeeRepository
{
    public void Save(Employee emp) { }
}

OOpen/Closed Principle (OCP)

Definition: Software entities should be open for extension but closed for modification.

Why It Matters:

  • Add new features without changing existing code
  • Reduces risk of breaking existing functionality
  • Promotes use of abstractions and polymorphism
❌ Violating OCP 
public class AreaCalculator
{
    public double Calculate(object shape)
    {
        // Must modify this method for every new shape!
        if (shape is Rectangle rect)
            return rect.Width * rect.Height;
        else if (shape is Circle circle)
            return Math.PI * circle.Radius * circle.Radius;
        else if (shape is Triangle tri)
            return 0.5 * tri.Base * tri.Height;
        // Adding new shape requires modification!
        throw new NotSupportedException();
    }
}
✅ Following OCP 
public interface IShape
{
    double CalculateArea();
}

public class Rectangle : IShape
{
    public double Width { get; set; }
    public double Height { get; set; }
    public double CalculateArea() => Width * Height;
}

public class Circle : IShape
{
    public double Radius { get; set; }
    public double CalculateArea() => 
        Math.PI * Radius * Radius;
}

// No modification needed - just extend!
public class AreaCalculator
{
    public double Calculate(IShape shape) => 
        shape.CalculateArea();
}

LLiskov Substitution Principle (LSP)

Definition: Objects of a superclass should be replaceable with objects of its subclasses without breaking the application.

Key Rules:

  • Preconditions cannot be strengthened in a subtype
  • Postconditions cannot be weakened in a subtype
  • Invariants of the supertype must be preserved
  • Subtype methods should not throw new exceptions
❌ Violating LSP 
public class Bird
{
    public virtual void Fly()
    {
        Console.WriteLine("Flying...");
    }
}

public class Penguin : Bird
{
    public override void Fly()
    {
        // Penguins can't fly! This breaks LSP
        throw new NotSupportedException(
            "Penguins cannot fly!");
    }
}

// This will crash!
void MakeBirdFly(Bird bird)
{
    bird.Fly(); // Throws exception for Penguin
}
✅ Following LSP 
public abstract class Bird
{
    public abstract void Move();
}

public interface IFlyable
{
    void Fly();
}

public class Sparrow : Bird, IFlyable
{
    public override void Move() => Fly();
    public void Fly() => 
        Console.WriteLine("Flying...");
}

public class Penguin : Bird
{
    public override void Move() => 
        Console.WriteLine("Swimming...");
}

// Now all Birds can Move() safely
void MakeBirdMove(Bird bird)
{
    bird.Move(); // Works for all birds!
}

IInterface Segregation Principle (ISP)

Definition: Clients should not be forced to depend on interfaces they do not use. Split large interfaces into smaller, specific ones.

Benefits:

  • More cohesive interfaces
  • Classes implement only what they need
  • Easier to understand and maintain
  • Reduced coupling
❌ Violating ISP 
// Fat interface - too many responsibilities
public interface IWorker
{
    void Work();
    void Eat();
    void Sleep();
    void GetPaid();
}

public class HumanWorker : IWorker
{
    public void Work() { /* OK */ }
    public void Eat() { /* OK */ }
    public void Sleep() { /* OK */ }
    public void GetPaid() { /* OK */ }
}

public class Robot : IWorker
{
    public void Work() { /* OK */ }
    // Robots don't eat or sleep!
    public void Eat() => throw new NotImplementedException();
    public void Sleep() => throw new NotImplementedException();
    public void GetPaid() => throw new NotImplementedException();
}
✅ Following ISP 
// Segregated interfaces
public interface IWorkable
{
    void Work();
}

public interface IFeedable
{
    void Eat();
    void Sleep();
}

public interface IPayable
{
    void GetPaid();
}

// Human implements all relevant interfaces
public class HumanWorker : IWorkable, IFeedable, IPayable
{
    public void Work() { }
    public void Eat() { }
    public void Sleep() { }
    public void GetPaid() { }
}

// Robot only implements what it needs
public class Robot : IWorkable
{
    public void Work() { }
}

DDependency Inversion Principle (DIP)

Definition: High-level modules should not depend on low-level modules. Both should depend on abstractions. Abstractions should not depend on details.

Key Concepts:

  • Dependency Injection (DI): Providing dependencies from outside rather than creating them inside
  • Inversion of Control (IoC): Framework controls the flow, not your code
  • Abstractions: Interfaces or abstract classes that define contracts
❌ Violating DIP 
// High-level module depends on low-level
public class EmailNotification
{
    public void Send(string message)
    {
        // Send email logic
    }
}

public class OrderService
{
    // Tight coupling to EmailNotification
    private readonly EmailNotification _notification 
        = new EmailNotification();
    
    public void PlaceOrder(Order order)
    {
        // Process order...
        _notification.Send("Order placed!");
        // Cannot easily switch to SMS!
    }
}
✅ Following DIP 
// Abstraction
public interface INotificationService
{
    void Send(string message);
}

public class EmailNotification : INotificationService
{
    public void Send(string message) { /* Email */ }
}

public class SmsNotification : INotificationService
{
    public void Send(string message) { /* SMS */ }
}

public class OrderService
{
    private readonly INotificationService _notification;
    
    // Dependency Injection via constructor
    public OrderService(INotificationService notification)
    {
        _notification = notification;
    }
    
    public void PlaceOrder(Order order)
    {
        // Process order...
        _notification.Send("Order placed!");
    }
}

🔧 DI Container Example (.NET)

// In Program.cs or Startup.cs
services.AddScoped<INotificationService, EmailNotification>();
services.AddScoped<OrderService>();

// Now OrderService gets INotificationService automatically injected!

🏗️ Creational Design Patterns

Creational patterns deal with object creation mechanisms, trying to create objects in a manner suitable to the situation.

Creational

🔒 Singleton Pattern

Purpose: Ensure a class has only one instance and provide a global point of access to it.

When to Use:

  • Database connections
  • Configuration managers
  • Logging services
  • Caching
public sealed class Singleton
{
    // Lazy<T> ensures thread safety
    private static readonly Lazy<Singleton> _instance
        = new Lazy<Singleton>(() => new Singleton());
    
    // Private constructor prevents external instantiation
    private Singleton() { }
    
    public static Singleton Instance => _instance.Value;
    
    public void DoSomething()
    {
        Console.WriteLine("Singleton method called");
    }
}

// Usage
Singleton.Instance.DoSomething();
⚠️ Warning: Singletons can make unit testing difficult. Consider using DI containers instead.
Creational

🏭 Factory Method Pattern

Purpose: Define an interface for creating an object, but let subclasses decide which class to instantiate.

When to Use:

  • When you don't know exact types at compile time
  • When you want to delegate creation to subclasses
  • To avoid tight coupling to concrete classes
// Product interface
public interface IVehicle
{
    void Drive();
}

// Concrete products
public class Car : IVehicle
{
    public void Drive() => Console.WriteLine("Driving car");
}

public class Motorcycle : IVehicle
{
    public void Drive() => Console.WriteLine("Riding motorcycle");
}

// Factory
public abstract class VehicleFactory
{
    public abstract IVehicle CreateVehicle();
}

public class CarFactory : VehicleFactory
{
    public override IVehicle CreateVehicle() => new Car();
}

public class MotorcycleFactory : VehicleFactory
{
    public override IVehicle CreateVehicle() => new Motorcycle();
}

// Usage
VehicleFactory factory = new CarFactory();
IVehicle vehicle = factory.CreateVehicle();
vehicle.Drive(); // "Driving car"
Creational

🏭🏭 Abstract Factory Pattern

Purpose: Provide an interface for creating families of related objects without specifying their concrete classes.

Key Difference from Factory Method:

  • Creates families of related objects
  • Multiple factory methods in one interface
  • Ensures products from same family work together
// Abstract products
public interface IButton { void Render(); }
public interface ITextBox { void Render(); }

// Concrete products - Windows family
public class WindowsButton : IButton
{
    public void Render() => Console.WriteLine("Windows Button");
}
public class WindowsTextBox : ITextBox
{
    public void Render() => Console.WriteLine("Windows TextBox");
}

// Concrete products - Mac family
public class MacButton : IButton
{
    public void Render() => Console.WriteLine("Mac Button");
}
public class MacTextBox : ITextBox
{
    public void Render() => Console.WriteLine("Mac TextBox");
}

// Abstract factory
public interface IUIFactory
{
    IButton CreateButton();
    ITextBox CreateTextBox();
}

// Concrete factories
public class WindowsFactory : IUIFactory
{
    public IButton CreateButton() => new WindowsButton();
    public ITextBox CreateTextBox() => new WindowsTextBox();
}

public class MacFactory : IUIFactory
{
    public IButton CreateButton() => new MacButton();
    public ITextBox CreateTextBox() => new MacTextBox();
}
Creational

🔨 Builder Pattern

Purpose: Separate the construction of a complex object from its representation, allowing the same construction process to create different representations.

When to Use:

  • Object has many optional parameters
  • Object creation involves multiple steps
  • Want to avoid "telescoping constructors"
  • Creating immutable objects
public class Pizza
{
    public string Size { get; }
    public string Crust { get; }
    public bool Cheese { get; }
    public bool Pepperoni { get; }
    public bool Mushrooms { get; }
    
    private Pizza(PizzaBuilder builder)
    {
        Size = builder.Size;
        Crust = builder.Crust;
        Cheese = builder.Cheese;
        Pepperoni = builder.Pepperoni;
        Mushrooms = builder.Mushrooms;
    }
    
    public class PizzaBuilder
    {
        public string Size { get; private set; } = "Medium";
        public string Crust { get; private set; } = "Regular";
        public bool Cheese { get; private set; }
        public bool Pepperoni { get; private set; }
        public bool Mushrooms { get; private set; }
        
        public PizzaBuilder SetSize(string size)
        { Size = size; return this; }
        
        public PizzaBuilder SetCrust(string crust)
        { Crust = crust; return this; }
        
        public PizzaBuilder AddCheese()
        { Cheese = true; return this; }
        
        public PizzaBuilder AddPepperoni()
        { Pepperoni = true; return this; }
        
        public PizzaBuilder AddMushrooms()
        { Mushrooms = true; return this; }
        
        public Pizza Build() => new Pizza(this);
    }
}

// Usage - Fluent API
var pizza = new Pizza.PizzaBuilder()
    .SetSize("Large")
    .SetCrust("Thin")
    .AddCheese()
    .AddPepperoni()
    .Build();
Creational

📋 Prototype Pattern

Purpose: Create new objects by copying an existing object (prototype) rather than creating from scratch.

When to Use:

  • Object creation is expensive
  • Objects have few variations
  • Avoiding subclasses for object creation
public interface IPrototype<T>
{
    T Clone();
}

public class Document : IPrototype<Document>
{
    public string Title { get; set; }
    public string Content { get; set; }
    public List<string> Authors { get; set; }
    
    // Shallow copy
    public Document ShallowClone()
    {
        return (Document)MemberwiseClone();
    }
    
    // Deep copy
    public Document Clone()
    {
        return new Document
        {
            Title = Title,
            Content = Content,
            Authors = new List<string>(Authors) // New list
        };
    }
}

// Usage
var original = new Document 
{ 
    Title = "Report", 
    Authors = new List<string> { "Alice" } 
};

var copy = original.Clone();
copy.Title = "Report Copy";
copy.Authors.Add("Bob");
// Original is not affected

🏛️ Structural Design Patterns

Structural patterns explain how to assemble objects and classes into larger structures while keeping these structures flexible and efficient.

Structural

🔌 Adapter Pattern

Purpose: Convert the interface of a class into another interface that clients expect. Allows incompatible interfaces to work together.

Real-world Analogy:

Like a power adapter that lets you plug a US device into a European outlet.

// Existing interface your code uses
public interface ITarget
{
    string GetRequest();
}

// Legacy/third-party class with incompatible interface
public class Adaptee
{
    public string GetSpecificRequest()
    {
        return "Specific request";
    }
}

// Adapter makes Adaptee compatible with ITarget
public class Adapter : ITarget
{
    private readonly Adaptee _adaptee;
    
    public Adapter(Adaptee adaptee)
    {
        _adaptee = adaptee;
    }
    
    public string GetRequest()
    {
        // Translate the call
        return $"Adapted: {_adaptee.GetSpecificRequest()}";
    }
}

// Usage
Adaptee adaptee = new Adaptee();
ITarget target = new Adapter(adaptee);
Console.WriteLine(target.GetRequest());
Structural

🎨 Decorator Pattern

Purpose: Attach additional responsibilities to an object dynamically. Provides a flexible alternative to subclassing for extending functionality.

When to Use:

  • Add responsibilities without affecting other objects
  • Responsibilities can be withdrawn
  • Extension by subclassing is impractical
// Component interface
public interface ICoffee
{
    string GetDescription();
    decimal GetCost();
}

// Concrete component
public class SimpleCoffee : ICoffee
{
    public string GetDescription() => "Simple Coffee";
    public decimal GetCost() => 2.00m;
}

// Base decorator
public abstract class CoffeeDecorator : ICoffee
{
    protected readonly ICoffee _coffee;
    
    protected CoffeeDecorator(ICoffee coffee)
    {
        _coffee = coffee;
    }
    
    public virtual string GetDescription() => _coffee.GetDescription();
    public virtual decimal GetCost() => _coffee.GetCost();
}

// Concrete decorators
public class MilkDecorator : CoffeeDecorator
{
    public MilkDecorator(ICoffee coffee) : base(coffee) { }
    
    public override string GetDescription() 
        => $"{_coffee.GetDescription()} + Milk";
    public override decimal GetCost() => _coffee.GetCost() + 0.50m;
}

public class SugarDecorator : CoffeeDecorator
{
    public SugarDecorator(ICoffee coffee) : base(coffee) { }
    
    public override string GetDescription() 
        => $"{_coffee.GetDescription()} + Sugar";
    public override decimal GetCost() => _coffee.GetCost() + 0.25m;
}

// Usage - Stack decorators!
ICoffee coffee = new SimpleCoffee();
coffee = new MilkDecorator(coffee);
coffee = new SugarDecorator(coffee);
// "Simple Coffee + Milk + Sugar" = $2.75
Structural

🏠 Facade Pattern

Purpose: Provide a unified interface to a set of interfaces in a subsystem. Defines a higher-level interface that makes the subsystem easier to use.

// Complex subsystem classes
public class CPU
{
    public void Freeze() => Console.WriteLine("CPU: Freeze");
    public void Jump(long position) { }
    public void Execute() => Console.WriteLine("CPU: Execute");
}

public class Memory
{
    public void Load(long position, byte[] data) 
        => Console.WriteLine("Memory: Load");
}

public class HardDrive
{
    public byte[] Read(long lba, int size) 
    {
        Console.WriteLine("HardDrive: Read");
        return new byte[size];
    }
}

// Facade - Simple interface to complex subsystem
public class ComputerFacade
{
    private readonly CPU _cpu = new();
    private readonly Memory _memory = new();
    private readonly HardDrive _hardDrive = new();
    
    public void Start()
    {
        _cpu.Freeze();
        _memory.Load(0, _hardDrive.Read(0, 1024));
        _cpu.Jump(0);
        _cpu.Execute();
        Console.WriteLine("Computer started!");
    }
}

// Usage - One simple method call
var computer = new ComputerFacade();
computer.Start();
Structural

🛡️ Proxy Pattern

Purpose: Provide a surrogate or placeholder for another object to control access to it.

Types of Proxies:

  • Virtual Proxy: Lazy initialization
  • Protection Proxy: Access control
  • Remote Proxy: Local representative for remote object
  • Logging Proxy: Add logging
public interface IDocument
{
    void Display();
}

// Real subject - expensive to create
public class RealDocument : IDocument
{
    private readonly string _filename;
    
    public RealDocument(string filename)
    {
        _filename = filename;
        LoadFromDisk(); // Expensive operation
    }
    
    private void LoadFromDisk()
    {
        Console.WriteLine($"Loading {_filename} from disk...");
        Thread.Sleep(2000); // Simulate slow load
    }
    
    public void Display() => Console.WriteLine($"Displaying {_filename}");
}

// Virtual proxy - lazy loading
public class DocumentProxy : IDocument
{
    private RealDocument? _realDocument;
    private readonly string _filename;
    
    public DocumentProxy(string filename)
    {
        _filename = filename;
    }
    
    public void Display()
    {
        // Load only when needed
        _realDocument ??= new RealDocument(_filename);
        _realDocument.Display();
    }
}

// Usage
IDocument doc = new DocumentProxy("huge_file.pdf");
// No loading yet...
doc.Display(); // Now it loads!
Structural

🌳 Composite Pattern

Purpose: Compose objects into tree structures to represent part-whole hierarchies. Lets clients treat individual objects and compositions uniformly.

public interface IFileSystemItem
{
    string Name { get; }
    long GetSize();
    void Display(int indent = 0);
}

// Leaf
public class File : IFileSystemItem
{
    public string Name { get; }
    public long Size { get; }
    
    public File(string name, long size)
    {
        Name = name;
        Size = size;
    }
    
    public long GetSize() => Size;
    public void Display(int indent = 0) 
        => Console.WriteLine($"{new string(' ', indent)}📄 {Name} ({Size}KB)");
}

// Composite
public class Directory : IFileSystemItem
{
    public string Name { get; }
    private readonly List<IFileSystemItem> _items = new();
    
    public Directory(string name) => Name = name;
    
    public void Add(IFileSystemItem item) => _items.Add(item);
    
    public long GetSize() => _items.Sum(i => i.GetSize());
    
    public void Display(int indent = 0)
    {
        Console.WriteLine($"{new string(' ', indent)}📁 {Name}/");
        foreach (var item in _items)
            item.Display(indent + 2);
    }
}

// Usage
var root = new Directory("root");
root.Add(new File("readme.txt", 10));

var src = new Directory("src");
src.Add(new File("app.cs", 50));
src.Add(new File("utils.cs", 30));
root.Add(src);

root.Display();
Console.WriteLine($"Total: {root.GetSize()}KB");
Structural

🌉 Bridge Pattern

Purpose: Decouple an abstraction from its implementation so that the two can vary independently.

Key Concept:

Prefer composition over inheritance. The "bridge" is the composition relationship.

// Implementor - the "implementation" hierarchy
public interface IMessageSender
{
    void SendMessage(string message);
}

public class EmailSender : IMessageSender
{
    public void SendMessage(string message) 
        => Console.WriteLine($"📧 Email: {message}");
}

public class SmsSender : IMessageSender
{
    public void SendMessage(string message) 
        => Console.WriteLine($"📱 SMS: {message}");
}

// Abstraction - the "abstraction" hierarchy
public abstract class Message
{
    protected readonly IMessageSender _sender;
    
    protected Message(IMessageSender sender)
    {
        _sender = sender;
    }
    
    public abstract void Send(string message);
}

public class TextMessage : Message
{
    public TextMessage(IMessageSender sender) : base(sender) { }
    
    public override void Send(string message)
    {
        _sender.SendMessage(message);
    }
}

public class UrgentMessage : Message
{
    public UrgentMessage(IMessageSender sender) : base(sender) { }
    
    public override void Send(string message)
    {
        _sender.SendMessage($"🚨 URGENT: {message}");
    }
}

// Usage - Mix and match freely!
var urgentEmail = new UrgentMessage(new EmailSender());
var normalSms = new TextMessage(new SmsSender());
urgentEmail.Send("Server down!");
normalSms.Send("Hello!");

🎭 Behavioral Design Patterns

Behavioral patterns are concerned with algorithms and the assignment of responsibilities between objects.

Behavioral

🎯 Strategy Pattern

Purpose: Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it.

// Strategy interface
public interface IPaymentStrategy
{
    void Pay(decimal amount);
}

// Concrete strategies
public class CreditCardPayment : IPaymentStrategy
{
    private readonly string _cardNumber;
    
    public CreditCardPayment(string cardNumber)
    {
        _cardNumber = cardNumber;
    }
    
    public void Pay(decimal amount)
    {
        Console.WriteLine($"💳 Paid ${amount} with card {_cardNumber}");
    }
}

public class PayPalPayment : IPaymentStrategy
{
    private readonly string _email;
    
    public PayPalPayment(string email) => _email = email;
    
    public void Pay(decimal amount)
    {
        Console.WriteLine($"🅿️ Paid ${amount} via PayPal ({_email})");
    }
}

// Context
public class ShoppingCart
{
    private IPaymentStrategy? _paymentStrategy;
    
    public void SetPaymentStrategy(IPaymentStrategy strategy)
    {
        _paymentStrategy = strategy;
    }
    
    public void Checkout(decimal total)
    {
        _paymentStrategy?.Pay(total);
    }
}

// Usage - Change strategy at runtime
var cart = new ShoppingCart();
cart.SetPaymentStrategy(new CreditCardPayment("1234-5678"));
cart.Checkout(99.99m);

cart.SetPaymentStrategy(new PayPalPayment("user@email.com"));
cart.Checkout(49.99m);
Behavioral

👀 Observer Pattern

Purpose: Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.

// Observer interface
public interface IObserver
{
    void Update(string message);
}

// Subject interface
public interface ISubject
{
    void Attach(IObserver observer);
    void Detach(IObserver observer);
    void Notify();
}

// Concrete subject
public class NewsAgency : ISubject
{
    private readonly List<IObserver> _observers = new();
    private string _latestNews = string.Empty;
    
    public string LatestNews
    {
        get => _latestNews;
        set
        {
            _latestNews = value;
            Notify();
        }
    }
    
    public void Attach(IObserver observer) => _observers.Add(observer);
    public void Detach(IObserver observer) => _observers.Remove(observer);
    public void Notify()
    {
        foreach (var observer in _observers)
            observer.Update(_latestNews);
    }
}

// Concrete observers
public class NewsChannel : IObserver
{
    public string Name { get; }
    
    public NewsChannel(string name) => Name = name;
    
    public void Update(string message)
    {
        Console.WriteLine($"📺 {Name}: Breaking - {message}");
    }
}

// Usage
var agency = new NewsAgency();
agency.Attach(new NewsChannel("CNN"));
agency.Attach(new NewsChannel("BBC"));

agency.LatestNews = "C# 12 Released!";
// Both channels receive the update
Behavioral

📜 Command Pattern

Purpose: Encapsulate a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations.

// Command interface
public interface ICommand
{
    void Execute();
    void Undo();
}

// Receiver
public class TextEditor
{
    public string Text { get; set; } = string.Empty;
    
    public void AddText(string text)
    {
        Text += text;
        Console.WriteLine($"Text: '{Text}'");
    }
    
    public void RemoveText(int length)
    {
        Text = Text[..^length];
        Console.WriteLine($"Text: '{Text}'");
    }
}

// Concrete command
public class AddTextCommand : ICommand
{
    private readonly TextEditor _editor;
    private readonly string _text;
    
    public AddTextCommand(TextEditor editor, string text)
    {
        _editor = editor;
        _text = text;
    }
    
    public void Execute() => _editor.AddText(_text);
    public void Undo() => _editor.RemoveText(_text.Length);
}

// Invoker with history
public class CommandManager
{
    private readonly Stack<ICommand> _history = new();
    
    public void ExecuteCommand(ICommand command)
    {
        command.Execute();
        _history.Push(command);
    }
    
    public void Undo()
    {
        if (_history.TryPop(out var command))
            command.Undo();
    }
}

// Usage
var editor = new TextEditor();
var manager = new CommandManager();

manager.ExecuteCommand(new AddTextCommand(editor, "Hello "));
manager.ExecuteCommand(new AddTextCommand(editor, "World"));
manager.Undo(); // Removes "World"
Behavioral

🚦 State Pattern

Purpose: Allow an object to alter its behavior when its internal state changes. The object will appear to change its class.

// State interface
public interface IOrderState
{
    void Process(Order order);
    void Ship(Order order);
    void Deliver(Order order);
}

// Context
public class Order
{
    public IOrderState State { get; set; }
    
    public Order() => State = new NewOrderState();
    
    public void Process() => State.Process(this);
    public void Ship() => State.Ship(this);
    public void Deliver() => State.Deliver(this);
}

// Concrete states
public class NewOrderState : IOrderState
{
    public void Process(Order order)
    {
        Console.WriteLine("✅ Order processed");
        order.State = new ProcessedState();
    }
    public void Ship(Order o) => Console.WriteLine("❌ Process first!");
    public void Deliver(Order o) => Console.WriteLine("❌ Not ready!");
}

public class ProcessedState : IOrderState
{
    public void Process(Order o) => Console.WriteLine("Already processed");
    public void Ship(Order order)
    {
        Console.WriteLine("📦 Order shipped");
        order.State = new ShippedState();
    }
    public void Deliver(Order o) => Console.WriteLine("❌ Ship first!");
}

public class ShippedState : IOrderState
{
    public void Process(Order o) => Console.WriteLine("Already shipped");
    public void Ship(Order o) => Console.WriteLine("Already shipped");
    public void Deliver(Order order)
    {
        Console.WriteLine("🎉 Order delivered!");
        order.State = new DeliveredState();
    }
}

// Usage
var order = new Order();
order.Ship();    // "Process first!"
order.Process(); // "Order processed"
order.Ship();    // "Order shipped"
order.Deliver(); // "Order delivered!"
Behavioral

📋 Template Method Pattern

Purpose: Define the skeleton of an algorithm in a method, deferring some steps to subclasses. Lets subclasses redefine certain steps without changing the algorithm's structure.

// Abstract class with template method
public abstract class DataMiner
{
    // Template method - defines the algorithm skeleton
    public void Mine(string path)
    {
        OpenFile(path);
        ExtractData();
        ParseData();
        AnalyzeData();
        SendReport();
        CloseFile();
    }
    
    // Steps to be implemented by subclasses
    protected abstract void OpenFile(string path);
    protected abstract void ExtractData();
    protected abstract void CloseFile();
    
    // Default implementations (hooks)
    protected virtual void ParseData()
    {
        Console.WriteLine("Parsing data...");
    }
    
    protected virtual void AnalyzeData()
    {
        Console.WriteLine("Analyzing data...");
    }
    
    protected virtual void SendReport()
    {
        Console.WriteLine("Sending report...");
    }
}

// Concrete classes
public class CsvDataMiner : DataMiner
{
    protected override void OpenFile(string path)
        => Console.WriteLine($"Opening CSV: {path}");
    protected override void ExtractData()
        => Console.WriteLine("Reading CSV rows...");
    protected override void CloseFile()
        => Console.WriteLine("Closing CSV");
}

public class PdfDataMiner : DataMiner
{
    protected override void OpenFile(string path)
        => Console.WriteLine($"Opening PDF: {path}");
    protected override void ExtractData()
        => Console.WriteLine("Extracting PDF text...");
    protected override void CloseFile()
        => Console.WriteLine("Closing PDF");
}

// Usage
var csvMiner = new CsvDataMiner();
csvMiner.Mine("data.csv");

⛓️ Chain of Responsibility Pattern

Purpose: Avoid coupling the sender of a request to its receiver by giving more than one object a chance to handle the request. Chain the receiving objects and pass the request along the chain.

// Handler interface
public abstract class SupportHandler
{
    protected SupportHandler? _nextHandler;
    
    public SupportHandler SetNext(SupportHandler handler)
    {
        _nextHandler = handler;
        return handler;
    }
    
    public virtual void Handle(string issue, int severity)
    {
        _nextHandler?.Handle(issue, severity);
    }
}

// Concrete handlers
public class Level1Support : SupportHandler
{
    public override void Handle(string issue, int severity)
    {
        if (severity <= 1)
            Console.WriteLine($"📞 L1 Support handles: {issue}");
        else
            base.Handle(issue, severity);
    }
}

public class Level2Support : SupportHandler
{
    public override void Handle(string issue, int severity)
    {
        if (severity <= 3)
            Console.WriteLine($"👨‍💻 L2 Support handles: {issue}");
        else
            base.Handle(issue, severity);
    }
}

public class Manager : SupportHandler
{
    public override void Handle(string issue, int severity)
    {
        Console.WriteLine($"👔 Manager handles: {issue}");
    }
}

// Usage - Build the chain
var l1 = new Level1Support();
var l2 = new Level2Support();
var manager = new Manager();

l1.SetNext(l2).SetNext(manager);

l1.Handle("Password reset", 1);     // L1 handles
l1.Handle("System slow", 2);         // L2 handles
l1.Handle("Server down!", 5);        // Manager handles

🎛️ Mediator Pattern

Purpose: Define an object that encapsulates how a set of objects interact. Promotes loose coupling by keeping objects from referring to each other explicitly.

// Mediator interface
public interface IChatRoom
{
    void SendMessage(string message, User sender);
    void AddUser(User user);
}

// Colleague
public class User
{
    public string Name { get; }
    private readonly IChatRoom _chatRoom;
    
    public User(string name, IChatRoom chatRoom)
    {
        Name = name;
        _chatRoom = chatRoom;
        _chatRoom.AddUser(this);
    }
    
    public void Send(string message)
    {
        Console.WriteLine($"{Name} sends: {message}");
        _chatRoom.SendMessage(message, this);
    }
    
    public void Receive(string message, string from)
    {
        Console.WriteLine($"{Name} receives from {from}: {message}");
    }
}

// Concrete mediator
public class ChatRoom : IChatRoom
{
    private readonly List<User> _users = new();
    
    public void AddUser(User user) => _users.Add(user);
    
    public void SendMessage(string message, User sender)
    {
        foreach (var user in _users.Where(u => u != sender))
        {
            user.Receive(message, sender.Name);
        }
    }
}

// Usage
var chatRoom = new ChatRoom();
var alice = new User("Alice", chatRoom);
var bob = new User("Bob", chatRoom);
var charlie = new User("Charlie", chatRoom);

alice.Send("Hello everyone!");
// Bob and Charlie both receive the message

🔄 Iterator Pattern

Purpose: Provide a way to access the elements of an aggregate object sequentially without exposing its underlying representation.

// In C#, typically use IEnumerable<T>
public class BookCollection : IEnumerable<Book>
{
    private readonly List<Book> _books = new();
    
    public void Add(Book book) => _books.Add(book);
    
    // Using yield for custom iteration
    public IEnumerator<Book> GetEnumerator()
    {
        foreach (var book in _books)
        {
            yield return book;
        }
    }
    
    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();
    
    // Custom iterator - only fiction books
    public IEnumerable<Book> FictionBooks()
    {
        foreach (var book in _books)
        {
            if (book.IsFiction)
                yield return book;
        }
    }
    
    // Reverse iterator
    public IEnumerable<Book> Reverse()
    {
        for (int i = _books.Count - 1; i >= 0; i--)
        {
            yield return _books[i];
        }
    }
}

public record Book(string Title, bool IsFiction);

// Usage
var collection = new BookCollection();
collection.Add(new Book("1984", true));
collection.Add(new Book("Clean Code", false));
collection.Add(new Book("Dune", true));

foreach (var book in collection.FictionBooks())
{
    Console.WriteLine(book.Title);
}
// Output: "1984", "Dune"

📚 Quick Reference Summary

🏗️ Creational

  • Singleton: One instance only
  • Factory Method: Delegate creation to subclasses
  • Abstract Factory: Create families of objects
  • Builder: Step-by-step construction
  • Prototype: Clone existing objects

🏛️ Structural

  • Adapter: Convert interfaces
  • Decorator: Add responsibilities dynamically
  • Facade: Simplify complex subsystems
  • Proxy: Control access to object
  • Composite: Tree structures
  • Bridge: Separate abstraction from implementation

🎭 Behavioral

  • Strategy: Interchangeable algorithms
  • Observer: Notify dependents of changes
  • Command: Encapsulate requests
  • State: Alter behavior based on state
  • Template Method: Algorithm skeleton
  • Chain of Responsibility: Pass requests along chain
  • Mediator: Centralize communications
  • Iterator: Sequential access

A — Bits, Bytes, and Memory Addresses

  1. What is Memory (RAM)? RAM is a giant flat array of bytes, each uniquely numbered (its address). A 64-bit CPU can address up to 264 bytes (~18 exabytes). Every C# variable, object, JIT-compiled method, and string ultimately lives at some address in this array.
  2. Bits, Bytes, and Words 1 bit = 0 or 1. 1 byte = 8 bits (256 values). 1 word = the CPU's natural unit (8 bytes on x64). In C#: byte = 1 byte, char = 2 bytes (UTF-16), int = 4, long = 8, double = 8. Use sizeof(T) or Unsafe.SizeOf<T>() to check at runtime.
  3. Memory Addresses Each byte has a unique numeric address (e.g., 0x7ffe3a20). When you write int x = 42; inside a method, the JIT reserves 4 consecutive bytes on the stack at that address. In C# you can see addresses via unsafe { fixed (int* p = &x) { … } }.
  4. Endianness Multi-byte values are stored with the least-significant byte first on x86/x64 (little-endian). The integer 0x0A0B0C0D is stored as 0D 0C 0B 0A. C# exposes BitConverter.IsLittleEndian and BinaryPrimitives.ReverseEndianness() for manual byte-order conversions when talking to network protocols.
  5. Memory Alignment & Padding CPUs read data fastest when its address is a multiple of its size. The CLR adds invisible padding bytes inside structs to satisfy alignment: struct { byte a; int b; } occupies 8 bytes, not 5. You can control layout with [StructLayout(LayoutKind.Explicit)] and [FieldOffset(n)].
  6. Hexadecimal Notation Addresses and byte values are written in hex (0x…) — each hex digit maps to 4 bits. One byte = two hex digits (255 = 0xFF). In C# use 0xFF literals, value.ToString("X8") for hex strings, and the debugger's Memory window to inspect raw bytes.

B — CLR Process Memory Layout

  1. How a .NET Process Starts The OS launches the native host (dotnet.exe or the self-contained EXE), which loads the CLR (CoreCLR). The CLR initialises its managed heap, JIT compiler, GC, thread pool, and type system — then calls your Main() method. All of this happens in the same OS process address space.
  2. Native Code Region (JIT-Compiled) IL bytecode from your assemblies is JIT-compiled to native machine code on first call (or ahead-of-time with NativeAOT / ReadyToRun). This native code lives in executable memory pages. Tiered compilation compiles first to fast "Tier 0" code, then re-JITs hot methods as optimised "Tier 1" code.
  3. Managed Heap All reference-type objects (class, string, arrays, delegates) are allocated on the CLR's managed heap. The GC owns this region — it allocates, compacts, and frees objects here. The managed heap is subdivided into Small Object Heap (SOH) with Gen 0/1/2, and Large Object Heap (LOH) for objects ≥ 85,000 bytes.
  4. Thread Stacks Each thread gets its own stack (default 1 MB on Windows, 8 MB on Linux). Method locals that are value types (int, struct) live on the stack. The CLR's managed stack walker knows which stack slots hold GC references so the GC can update them during compaction.
  5. Loader Heap (Type Metadata) The CLR's Loader Heap stores Method Tables, EEClass structures, and MethodDescs — the metadata that describes every loaded type and method. This data is never GC'd; it lives for the lifetime of the AssemblyLoadContext. You can inspect it via !dumpmt in WinDbg/LLDB with SOS.
  6. Pinned Object Heap (POH) .NET 5+ introduced the POH for long-lived objects that must stay at a fixed address (pinned). Before POH, frequent pinning fragmented the SOH and hindered compaction. Allocate on POH via GC.AllocateArray<T>(length, pinned: true).

C — The Stack in C#

  1. Stack Frames (Activation Records) Every C# method call pushes a new frame onto the thread's stack. A frame holds: local value-type variables, saved registers, the return address, and references to heap objects. On return the frame is popped — all locals are instantly freed with zero overhead.
  2. What Lives on the Stack in C# Value-type locals (int, double, bool, DateTime, custom struct), method arguments (value-type copies or references to heap objects), ref/in/out parameters (managed pointers), and Span<T> / ref struct instances. The reference variable itself (8 bytes) also lives on the stack even when the object is on the heap.
  3. stackalloc — Stack Allocation in C# Span<byte> buf = stackalloc byte[256]; allocates 256 bytes directly on the current stack frame — no heap, no GC. The memory is freed automatically when the method returns. Use for small, short-lived buffers on hot paths. Guarded by a stack overflow check emitted by the JIT.
  4. Stack Size & StackOverflowException Each thread gets a fixed-size stack (default 1 MB on Windows, 8 MB on Linux). Unbounded recursion or very large stackalloc exhausts the stack, triggering an unrecoverable StackOverflowException. The CLR cannot catch this — the process terminates. Design recursive algorithms with depth limits or convert to iterative loops.
  5. ref, in, and out Parameters ref int x passes a managed pointer (byref) to the caller's stack slot. in is a read-only byref (avoids copying large structs). out is a write-only byref. Under the hood all three are a pointer to a stack address — zero allocation, zero copy. The JIT emits a lea to take the address.
  6. JIT Inlining & Stack Elimination The RyuJIT compiler inlines small methods (≤ ~100 IL bytes): the callee's code is merged into the caller's frame with no call/ret. This eliminates the frame push/pop overhead, enables register allocation across the boundary, and can remove dead code. [MethodImpl(MethodImplOptions.AggressiveInlining)] hints larger methods for inlining.

D — The CLR Managed Heap

  1. Allocation with new var obj = new MyClass(); — the CLR bumps the Gen 0 allocation pointer by the object's size, writes the object header + method-table pointer, zeroes the fields, and returns the reference. This is essentially a pointer-bump — extremely fast (no free-list search). The GC handles deallocation later.
  2. Object Layout on the Heap Every heap object begins with an 8-byte Object Header (sync block index for locking, hash code) and an 8-byte Method Table pointer (vtable, type info). Fields follow. So the minimum C# object (new object()) consumes 24 bytes on x64 (header + MT ptr + 8 bytes padding for alignment).
  3. Small Object Heap (SOH): Gen 0 / 1 / 2 Objects < 85,000 bytes land on the SOH. New objects start in Gen 0 (the nursery). Survivors of a Gen 0 collection are promoted to Gen 1, then to Gen 2. Gen 0 is small and collected frequently (microseconds); Gen 2 is large and collected rarely (can pause for milliseconds).
  4. Large Object Heap (LOH) Objects ≥ 85,000 bytes go directly to the LOH (also collected as Gen 2). The LOH is not compacted by default — allocations use a free-list, causing external fragmentation over time. Since .NET Core 2.1 you can opt in to LOH compaction via GCSettings.LargeObjectHeapCompactionMode.
  5. Pinned Object Heap (POH) Objects that must not be moved by the GC (for P/Invoke, I/O buffers) should use the POH: GC.AllocateArray<byte>(size, pinned: true). POH avoids fragmentation caused by pinning objects on the SOH. Introduced in .NET 5.
  6. Segments and GC Heap Budget The managed heap is made of variable-size segments (sometimes called regions in .NET 7+ DPAD GC). When Gen 0's allocation budget is exhausted, a Gen 0 collection triggers. The GC dynamically adjusts budgets based on survival rates and system memory pressure — you don't configure this directly.

E — References, ref, and Pointers in C#

  1. Object References A variable of a class type (string name = "hello";) holds an 8-byte reference (on x64) — essentially a pointer to the object on the managed heap. The GC can relocate the object and transparently update the reference. You cannot do arithmetic on it (unlike C pointers).
  2. ref Locals and Returns ref int r = ref array[0]; creates a managed pointer (byref) to the element — no copy. Modifying r modifies the array directly. ref return lets a method return a byref to a field or array slot. This avoids copying large structs while staying fully safe (the CLR tracks the reference for GC).
  3. in Parameters (Read-Only Ref) void Render(in Matrix4x4 m) passes a managed pointer to m without copying the 64-byte struct. The in modifier makes it read-only at the call site. Caution: if you pass a non-variable (e.g., a literal or expression), the compiler creates a hidden temporary copy — negating the benefit.
  4. null Reference null means the reference points to nothing (address 0). Accessing a member on null throws NullReferenceException — the CPU's null-page trap (address 0 is unmapped). C# 8+ nullable reference types (string?) catch this at compile time with warnings. Value types cannot be null unless wrapped in Nullable<T>.
  5. Span<T> — Fat Reference Span<T> is a ref struct holding a (managed pointer, length) pair — 16 bytes. It can point into arrays, stackalloc memory, or unmanaged buffers. Bounds-checked. Cannot escape to the heap (ref struct restriction). Used heavily in high-perf APIs (string.AsSpan(), Utf8JsonReader, Pipe).
  6. unsafe Pointers Inside an unsafe block, C# supports raw pointers: int* p = &x;, pointer arithmetic (p + 1), and dereferencing (*p). Use fixed (byte* ptr = array) to pin a managed object so the GC won't move it. Required for P/Invoke and very low-level perf code. Bypasses all safety — use with extreme caution.

F — Value Types vs Reference Types in C#

  1. Value Types (struct) — Stored Inline int, double, bool, DateTime, Guid, enum, and custom structs store their data directly at the variable's location — on the stack if local, or inline inside a containing object/array. Point p = new(3,7); — the x and y fields sit right there in the stack frame, no heap involved.
  2. Reference Types (class) — Pointer on Stack, Object on Heap class, string, arrays, delegates, and interfaces are reference types. The local variable is an 8-byte reference on the stack; the actual object lives on the managed heap. var a = new Node(99); var b = a; — both a and b point to the same heap object.
  3. Boxing & Unboxing When a value type is cast to object or an interface (object o = 42;), the CLR boxes it: allocates a heap object, copies the value inside, returns a reference. Unboxing (int x = (int)o;) copies back. Boxing creates GC pressure — avoid in loops. Generics (List<int> vs ArrayList) eliminate boxing entirely.
  4. Array Layout int[] arr = new int[4]; — the array is one contiguous heap object: header (16 bytes) + length field (8 bytes) + 4×4 = 16 bytes of data = 40 bytes total. Element arr[i] is at offset header + i*4. Value-type arrays are flat and cache-friendly. Reference-type arrays (Node[]) store references — each element is an 8-byte pointer to a separate heap object.
  5. string in Memory C# string is a reference type, immutable, stored as a UTF-16 char[] inline in the object. Header (16B) + length (4B) + chars (2B each) + null terminator (2B for interop). "hello" = 16+4+10+2 = 32 bytes on heap. String interning (string.Intern) deduplicates identical literals to share one heap allocation.
  6. Object Header & Method Table Every C# heap object starts with: Object Header (8 bytes — sync block index for lock, hash code) then Method Table pointer (8 bytes — points to the type's vtable, used for virtual dispatch, casting, and GC type info). The reference variable actually points to the Method Table pointer, not the very start of the header.
  7. record struct vs record class record struct is a value type (inline, stack) with compiler-generated Equals/GetHashCode/ToString. record class is a reference type (heap-allocated) with the same generated members. Choose record struct for small immutable DTOs (< 32 bytes) to avoid heap allocation; choose record class for larger objects or when shared identity matters.

G — The .NET Garbage Collector

  1. Reachability & GC Roots The .NET GC starts from roots: stack variables, static fields, GC handles, CPU registers, and finalisation queue entries. Any object reachable via a chain of references from a root is live. All other objects are dead and will be collected.
  2. Mark → Plan → Compact (SOH) Mark phase: walk from roots, mark each live object. Plan phase: decide which objects to promote and whether to compact or sweep. Compact phase: slide live objects together, eliminating gaps, then update all references. Compaction makes the SOH zero-fragmentation — subsequent allocation is a simple pointer bump.
  3. Generational Collection (Gen 0 / 1 / 2) Most objects die young. Gen 0 (few KB–MB) is collected constantly — pauses < 1 ms. Gen 1 (intermediate buffer) catches objects that survive briefly. Gen 2 + LOH is collected on full GC and can pause for tens of ms. The GC auto-tunes generation budgets to minimize pause time.
  4. Workstation vs Server GC <ServerGarbageCollection>true</…> in the project file enables Server GC: one managed heap + GC thread per CPU core for maximum throughput. Workstation GC uses a single thread and is optimised for low-latency desktop apps. Web servers and APIs almost always use Server GC.
  5. Background (Concurrent) GC Background GC runs Gen 2 collection concurrently with your application threads. It suspends threads only briefly for a marking phase, then sweeps/compacts without stopping the world. Enabled by default in both Workstation and Server modes since .NET Core 3.0.
  6. Finalizers & IDisposable Objects with a finalizer (~MyClass()) are added to the finalisation queue. After they become unreachable, the GC queues them for finalisation by a dedicated thread — the object survives an extra GC cycle. This delays collection and hurts perf. Always prefer IDisposable + using for deterministic cleanup of unmanaged resources.
  7. GC.Collect() and When to Force GC Calling GC.Collect() forces a full collection — almost always a mistake. The GC's heuristics are nearly always better than manual triggers. The one legitimate scenario: after a large one-time operation (e.g., loading a level in a game) to pay the GC cost once rather than mid-frame. Use GC.TryStartNoGCRegion to temporarily suppress GC in latency-critical sections.
  8. GC Pinning & fixed fixed (byte* ptr = array) pins the array so the GC cannot move it — required for passing buffers to unmanaged code via P/Invoke. Pinned objects fragment the SOH because the compactor must work around them. Minimise pinning duration; prefer the POH for long-lived pins.

H — CPU Registers and the Instruction Cycle

  1. Registers — Memory Inside the CPU Registers are tiny, ultra-fast memory cells inside the CPU die. A modern x86-64 CPU has 16 general-purpose 64-bit registers (rax, rbx, rcx, rdx, rsi, rdi, rsp, rbp, r8–r15) plus 16 SIMD registers and special-purpose ones. Access time is under 1 CPU cycle — vs. ~4 cycles for L1 cache, ~200+ for RAM.
  2. The Fetch–Decode–Execute Cycle Every instruction goes through: Fetch — load next instruction from memory at address in Program Counter (PC/RIP); Decode — CPU figures out what operation and operands; Execute — ALU performs the work; Write-back — result stored in a register or memory. PC is incremented to the next instruction.
  3. The Load/Store Model Most ISAs (x86, ARM) operate on registers only — you cannot add two memory addresses directly. You first load values from memory into registers, operate on the registers using ALU instructions, then store a result register back to memory. Memory ↔ register is the key bottleneck.
  4. Stack Instructions: PUSH / POP / CALL / RET PUSH rax: rsp -= 8 then writes rax to [rsp]. POP reverses it. CALL addr: pushes the next PC onto the stack (return address), then jumps to addr. RET: pops the return address from stack and jumps to it. The entire call stack is just these primitives.
  5. Out-of-Order Execution & Microarchitecture Modern CPUs don't execute instructions strictly in program order. The CPU looks ahead, finds independent instructions, and runs them in parallel (superscalar). Results are committed in order to preserve program semantics. This "out-of-order engine" is why branch mispredictions and data hazards are expensive — they flush the pipeline.
  6. The Memory Bus and Latency When a CPU needs a value not in cache, it issues a memory request on the bus. The memory controller fetches an entire 64-byte cache line from RAM. At ~3 GHz, a cache miss costs ~200+ nanoseconds — roughly 600+ cycles of nothing. This is why memory access patterns dominate performance far more than raw instruction count.

I — CPU Caches and Memory Locality

  1. Cache Lines The CPU never fetches a single byte from RAM — it fetches a 64-byte cache line (the block of 64 contiguous bytes containing the requested address). If you iterate an array sequentially, subsequent elements are already in the cache line — effectively free. This is spatial locality.
  2. Spatial Locality Accessing data near recently accessed data. Iterating int[] arr sequentially is cache-friendly: each 64-byte cache line holds 16 ints. Iterating a LinkedList<T> is not — each node is a separate heap object at a random address (pointer-chasing, one cache miss per node).
  3. Temporal Locality Reusing the same data within a short time window. A tight loop repeatedly reading the same variable keeps it in L1 cache. Long loops that touch huge datasets thrash the cache — each line is evicted before reuse. Blocking/tiling matrix algorithms are designed to maximise temporal locality.
  4. Cache-Associativity & Eviction Policy Caches are N-way set-associative: a cache line can map to one of N slots ("ways") in a set determined by address bits. When all N ways are full, the cache evicts one — usually LRU (Least Recently Used). Cache thrashing occurs when N+1 addresses all compete for the same set.
  5. False Sharing (Cache Line Contention) When two CPU cores write to different fields that share the same 64-byte cache line, the line bounces between cores' caches — the MESI coherence protocol forces invalidation on every write. In C# avoid this by padding with [StructLayout(LayoutKind.Explicit)] and explicit field offsets 64 bytes apart, or using separate arrays per thread.
  6. Prefetching: Hardware and Software Hardware prefetchers detect sequential access patterns and proactively load the next cache line. In C# you have no direct prefetch intrinsic, but using Span<T> and sequential for loops over arrays naturally triggers the hardware prefetcher. System.Runtime.Intrinsics.X86.Sse.Prefetch0() is available for advanced scenarios in .NET 7+.

J — Virtual Memory and Paging

  1. Virtual vs Physical Addresses Programs use virtual addresses — every process thinks it owns the full address space (0 to 264). The CPU's MMU (Memory Management Unit) translates virtual to physical addresses transparently on every memory access, using a per-process page table set by the OS.
  2. Pages and Page Tables Memory is divided into 4 KB pages (or huge pages: 2 MB / 1 GB). The page table maps each virtual page to a physical page frame. A four-level x86-64 page table (PGD → PUD → PMD → PTE) is walked on each translation miss. TLB caches recent translations.
  3. TLB — Translation Lookaside Buffer The TLB is a small hardware cache (~64–1024 entries) of recent virtual→physical translations. A TLB hit completes in 1 cycle; a TLB miss triggers a full 4-level page-table walk (~hundreds of cycles). Code that accesses thousands of memory pages thrashes the TLB severely.
  4. Demand Paging & Page Faults The OS does not load all program pages into RAM immediately. When a virtual address is accessed for the first time, the MMU finds no physical mapping and raises a page fault. The OS kernel handles it: allocates a physical frame, loads the data (from file or zeroes), updates the page table, and resumes the instruction. Transparent to the programmer.
  5. Memory Protection & Isolation Page table entries carry permission bits: read (R), write (W), execute (X). Attempting to write to a read-only page faults (SIGSEGV). The W^X policy (write XOR execute) enforced by modern OSes prevents code injection: data pages cannot be executed, code pages cannot be written — defeats many buffer-overflow exploits.
  6. Swap / Paging to Disk When physical RAM is full, the OS evicts (swaps out) a page to disk and reuses its physical frame. Accessing a swapped-out page causes a major page fault — the OS reads it back from disk. This can cause severe slowdowns ("thrashing") when the working set exceeds available RAM by a large margin.
  7. Copy-on-Write (COW) After fork(), parent and child share physical pages marked read-only. On the first write by either process, the MMU fires a write-protection fault; the OS copies that one page, gives the writer its own copy, and makes it writable. COW makes fork() nearly instant regardless of process size.

K — Memory Safety in C#

  1. Safe by Default In safe C#, the CLR enforces bounds checking on arrays, prevents pointer arithmetic, and the GC eliminates use-after-free and double-free. You cannot corrupt the heap via normal code. All the classic C/C++ memory bugs (buffer overflows, dangling pointers, uninitialised reads) are structurally impossible in safe C#.
  2. NullReferenceException The most common memory-related exception in C#. Accessing a member on a null reference triggers a hardware trap (address 0 is unmapped) which the CLR converts to NullReferenceException. Enable nullable reference types (#nullable enable) to catch most null issues at compile time via warnings.
  3. IndexOutOfRangeException Every array and Span<T> access is bounds-checked by the JIT. Accessing arr[i] where i < 0 || i >= arr.Length throws IndexOutOfRangeException. The JIT eliminates the bounds check when it can prove the index is in-range (e.g., a standard for (int i = 0; i < arr.Length; i++) loop).
  4. Managed Memory Leaks GC prevents true leaks, but you can still have "managed leaks": objects that are technically reachable but no longer needed. Common culprits: static List<T> that grows forever, event handlers not unsubscribed (publisher.Event += handler), closures capturing variables, and ConcurrentDictionary entries never removed.
  5. IDisposable and Unmanaged Resource Leaks The GC manages memory but not OS handles (files, sockets, DB connections). Objects holding unmanaged resources implement IDisposable. Failing to call Dispose() / using leaks handles. The finalizer is a safety net but runs non-deterministically and adds GC overhead. Always use using var stream = new FileStream(…);.
  6. StackOverflowException Unbounded recursion fills the 1 MB thread stack. The CLR detects this but cannot catch or recover from it — the process terminates. In ASP.NET this kills the worker process. Always guard recursive methods with a depth counter or convert to an iterative Stack<T>-based algorithm.
  7. unsafe Code Risks Inside unsafe blocks all bets are off: buffer overflows, dangling pointers, heap corruption are all possible. unsafe requires explicit opt-in (<AllowUnsafeBlocks>true</…>) and should be confined to a small, well-tested surface. Prefer Span<T>, Memory<T>, and NativeMemory APIs which provide similar perf without unsafe.
  8. OutOfMemoryException Thrown when the CLR cannot allocate a new object — either the process is out of virtual address space, or the OS is out of commit memory. Common triggers: huge arrays, LOH fragmentation, and runaway allocations in loops. Profile with dotnet-counters (gc-heap-size) and dotnet-dump to diagnose.

L — C# / .NET CLR Deep Dive

  1. Span<T> and Memory<T> Span<T> is a ref struct (stack-only) — a (pointer, length) pair giving safe, bounds-checked access to contiguous memory (arrays, stackalloc, native buffers). Memory<T> is the heap-safe sibling that can be stored in fields and used in async methods. Both avoid allocating new arrays for slicing: arr.AsSpan(2, 5) is zero-copy.
  2. ArrayPool<T> — Rent, Don't Allocate ArrayPool<T>.Shared.Rent(size) returns a reusable array from a pool, avoiding GC pressure. Call .Return(array) when done. Extensively used inside ASP.NET Core, System.Text.Json, and Kestrel. For hot paths, this eliminates thousands of Gen 0 allocations per second.
  3. stackalloc and Stack-Based Buffers Span<char> buf = stackalloc char[128]; — allocates on the stack frame, freed on method return, zero GC cost. Ideal for small temporary buffers (string formatting, crypto operations). Guard with a size check: fall back to ArrayPool if the size exceeds a threshold (~256 bytes).
  4. ref struct — Stack-Only Types A ref struct can never be boxed, stored in a field of a class, or captured by a closure/async state machine. This guarantees it lives only on the stack. Span<T>, ReadOnlySpan<T>, and custom ref struct types give struct-of-pointers semantics with zero heap allocation risk.
  5. NativeMemory and Marshal NativeMemory.Alloc(byteCount) allocates unmanaged memory (like C's malloc). The GC is unaware of it — you must free it with NativeMemory.Free(ptr). Use for P/Invoke interop, custom allocators, or bypassing GC pressure. Marshal.AllocHGlobal / Marshal.FreeHGlobal serve the same purpose (older API).
  6. Unsafe.SizeOf<T>() and StructLayout Unsafe.SizeOf<MyStruct>() returns the size including padding. [StructLayout(LayoutKind.Sequential, Pack = 1)] eliminates padding (useful for binary protocols). [StructLayout(LayoutKind.Explicit)] + [FieldOffset] gives C-union semantics — overlapping fields share the same memory.
  7. Closures & Async State Machines — Hidden Allocations A lambda that captures a local variable generates a hidden class (display class) storing the captured variable — a heap allocation on each invocation. async methods generate a state-machine struct that is boxed on the first await that doesn't complete synchronously. Use ValueTask and static lambdas to mitigate.
  8. string Allocation Patterns Every string concatenation (a + b) allocates a new string object. string.Concat / $"{x}" in a loop creates N heap objects. Use StringBuilder for multi-step composition, string.Create for single-allocation formatting, and ReadOnlySpan<char> / Utf8JsonWriter to avoid strings entirely in serialisation paths.
  9. Memory Profiling Tools for .NET dotnet-counters — live GC/heap metrics. dotnet-dump + dotnet-gcdump — heap snapshots. dotnet-trace — ETW/EventPipe tracing. JetBrains dotMemory — visual heap/allocation analysis. PerfView — GC event analysis, allocation stacks. Visual Studio Diagnostic Tools — integrated memory snapshots while debugging.
  10. Memory-Mapped Files in C# MemoryMappedFile.CreateFromFile("data.bin") maps a file directly into the virtual address space. Access via MemoryMappedViewAccessor or get a Span<T> from CreateViewAccessor().SafeMemoryMappedViewHandle. The OS pages-in data on demand — ideal for large files (databases, logs) without loading everything into RAM.

Key Insight: struct vs class Decision

Use struct for small (≤ ~16 bytes), immutable, frequently allocated data — lives on the stack, zero GC cost. Use class for larger objects, objects with identity, or when shared references are needed. There is no single "right" answer — measure with dotnet-counters.

Key Insight: Indirection Is Expensive

Every reference dereference is a potential cache miss. Prefer flat data structures (List<T>, T[], arrays of structs) over LinkedList<T> or graphs of heap-allocated class nodes when iteration performance matters.

Key Insight: Hidden Allocations Kill Perf

Lambdas capturing locals, async state machines, params object[], boxing int→object, LINQ closures — all allocate invisibly. Use [BenchmarkDotNet] with MemoryDiagnoser to find them. Prefer static lambdas, ValueTask, and Span<T> on hot paths.

Key Insight: GC Is Not Free

Each Gen 0 collection suspends all threads (briefly). High allocation rates → frequent Gen 0 GC → cumulative pause time. In ASP.NET Core, aim for zero allocations per request on hot paths. Pool buffers with ArrayPool<T>, reuse objects with ObjectPool<T>.

Key Insight: Span<T> Is Your Best Friend

Span<T> gives array-like access to any contiguous memory (managed, stack, native) with bounds checking and zero allocation for slicing. It replaces many unsafe usages with safe, high-performance code. Use .AsSpan() everywhere.

Key Insight: IDisposable Is Manual Memory Management

For unmanaged resources (files, sockets, DB connections, native memory), the GC does nothing. using var conn = new SqlConnection(…); is the C# equivalent of deterministic memory management. Forgetting using leaks OS handles — a managed memory leak in disguise.
